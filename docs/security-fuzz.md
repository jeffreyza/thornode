# Security fuzz targets

Run `FUZZ_TIME=20s FUZZ_CORPUS_DIR=/tmp/thornode-security-fuzz-corpus scripts/test-security-fuzz.sh` from the repository root. `FUZZ_TARGET=FuzzRPCVersion` selects one target. The default runs all five, one Go invocation per target. `FUZZ_TIME` accepts Go durations or iteration counts such as `1000x`. The runner stops on the first failure and Go writes reproducible failing inputs to the target package's `testdata/fuzz` directory. Keep useful minimized regressions there. The corpus directory keeps generated corpus inputs between runs; the script replaces this module's subtree of `$GOCACHE/fuzz` with it before fuzzing, copies that subtree back afterwards, and leaves the Go build cache where it is. Keep it outside the repository. An `Nx` budget is raised by the number of cached entries, because Go replays each once before mutating.

The targets exercise memo parsing, address parsing, Solana RPC version decoding, canonical FROST evidence decoding, and FROST signed statement tampering. They use no network service or mutable shared fixture. Inputs are capped at 512 bytes for memo and signed payload, 256 bytes for address, 1024 bytes for RPC version, and one byte above the protocol evidence limit for evidence. Larger generated inputs are skipped to keep campaigns practical. These targets do not cover every external chain RPC response, all memo variants, or signature cryptography.

Seed cases run in ordinary Go tests: `GOTOOLCHAIN=go1.26.10 GOMAXPROCS=4 go test -p 2 ./common ./x/thorchain/memo ./bifrost/pkg/chainclients/solana/rpc ./bifrost/p2p/messages`. CI can run the script with a fixed `FUZZ_TIME` and a persistent `FUZZ_CORPUS_DIR`; the CI workspace owns pipeline wiring.
